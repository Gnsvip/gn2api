## 文件和数据位置

- 开关、调度时间、最近结果：`/var/lib/modeltrace-ovh/state.sqlite3`，目录仅服务账号可读。
- 服务环境：`/etc/modeltrace-ovh.env`，没有数据库密码或模型密钥。
- 自动停调度凭据：`/etc/modeltrace-ovh/sub2api-admin-key`（root 0600），经 systemd `LoadCredential` 只读提供给独立服务；不进入网页、环境变量或 SQLite。
- 前端：`/opt/sub2api-custom/modeltrace.js`。
- Nginx：主站增加该脚本和 `/custom/modeltrace/api/` 到 `127.0.0.1:17861` 的代理。

## 来源与结果解释

归因算法和指纹库直接使用 [xqy2006/ModelTrace](https://github.com/xqy2006/ModelTrace)，固定 commit `6cd4a8ff0f3f4e49d6d6969dd2fbadfa1569fde2`；原始 `fingerprint.py`、`data/unified_bank.json` 和 MIT LICENSE 保存在 `vendor/`。

集成层只负责指定账号的请求适配、管理员权限、调度、结果保存与页面显示。没有运行模型推理引擎，也没有采用任务监控插件。

- 绿：凑齐所选 1、2 或 3 份有效样本，最高归因与预期一致，候选库内分数至少 0.80，领先第二名至少 0.25。沿用原版 ModelTrace 对 1、2、3 份回答分别提供的校准，没有降低数字有效性、分数或差距阈值。较少样本更容易误判；这是显示阈值，不是真伪保证。
- 黄：区分度不足、样本不足、连接/流内错误、实际限流/冷却或上游拒绝、复测结果不稳定。
- 样本不足时显示「识别 N 个，至少需要 M 个（本次要求 K 个）」；门槛沿用 ModelTrace 原版的 `max(80, ceil(K × 0.55))`，没有降低。已识别的上游错误码（繁忙、限流、额度或点数不足等）显示对应原因，其余维持通用提示，不回显原始上游错误或任何凭据。旧历史因未保存实际数量，不能追补计数。
- 完整回答的有效数字不足时，保留本轮已成功的回答，换新挑战只补采缺少部分；凑齐所选份数后才评分。不拼接不足的回答，不跨轮缓存样本。初测、补采、不符复测共用所选次数两倍的请求上限和 240 秒预算。初测补采后若疑似不符，但剩余次数不足以再取得同样份数的独立回答，就记黄点；复测样本不足同样记黄点，均不会触发自动停调度。HTTP、流内错误和超时不补采。新结果保存挑战设置、请求上限，并显示请求数、有效挑战回答数（含复测）和数字样本不足次数，旧记录保持兼容。
- 红：首次高分不符后，再采与所选次数相同份数的独立样本；同一其他模型再次以足够区分度胜出。1、2 次模式仍需完整独立复测才能计红，不能只凭初测停调度。
- 没有记录不填点；关闭后历史点淡显；超过所设间隔两倍（最少 5 分钟）未有当前模型的新结果时标记过期。换模型后旧模型结果淡显，悬停可识别。

库内目前 18 个 GPT/Claude 型号，尚无 `gpt-6.1-sol`、Gemini、Grok。库外模型不能认证。候选库内概率不是“真模型概率”；第三方混用模型、提示词和接口环境差异都可能影响结果。模型列表在打开设置时与 sub2api 的实际可用模型取交集。

## 连续不符自动停止调度

点击账号行的「模型归因」，可以独立开启「连续不符自动停止调度」，默认关闭，默认阈值 **3 轮**，可改为 1–100。需要同时开启该账号的模型归因检测才会工作。

只累计已复测仍不符的红点，绿色和黄色均清零。开启或调整开关、阈值、检测模型、挑战次数后，从新结果开始计数；旧历史不追算。更改挑战次数会作废旧任务并阻止其后续请求，保留下一轮原计划时间，不额外提前付费检测；已发出的请求可能已计费。账号路由/凭据配置变化、进程中断的检测也不能延续旧计数；普通 OAuth token 刷新不影响。计数独立持久化，不受十条历史上限影响。

达到阈值，通过本机 sub2api 原生 `POST /api/v1/admin/accounts/:id/schedulable` 设置 `schedulable=false`。此接口同步调度快照并发出变更事件。仅停止给该账号分配新业务，不终止已有流；该账号的归因检测同时暂停，保留原因、时间和历史。不会自动恢复账号调度。管理员排查后，须在 sub2api 手动恢复调度，再开启模型归因，计数从零开始。

接口未确认成功时，显示「停调度未确认」，每 60 秒重试。关闭自动停止或检测开关可取消待执行动作；此操作不会恢复已经停止的业务调度。动作与设置写入串行处理，已经发出的停调度操作无法撤销。新设置保存成功后，旧任务不能继续触发。阈值和配置不变的重复保存保持幂等。调整自动停止策略不额外提前下一轮检测。

管理员 API key 只供固定本机能力检查、账号测试和停调度接口使用，程序没有恢复、删除或批量修改账号的路径。此密钥本身是 sub2api 全局管理员密钥，须保护系统凭据及服务账号；如在 sub2api 轮换密钥，应同步 root 0600 凭据文件并仅重启 `modeltrace-ovh`。PostgreSQL 仍只有原来的列级只读权限。

历史升级脚本 `upgrade_auto_pause.py` 和 `auto-pause.conf` 用于首次添加自动停止。后续 `upgrade_interval.py` 增加间隔设置并移除百分比限制，`upgrade_sampling.py` 增加同轮补采；均等待正在执行的检测结束，备份程序、前端、SQLite，再仅重启独立服务。无需重启 sub2api 或服务器。`upgrade_compact_ui.py` 仅发布前端与说明文件，不重启独立归因服务，也不写入数据库。Cloudflare 会覆盖源站静态脚本的 no-cache，当前页面引用为 `modeltrace.js?v=20261020-2`，先检查 Nginx 配置再平滑 reload，主进程不重启。以后更改脚本也应更新版本号。

上线后在 `/admin/accounts` 账号管理页面刷新以加载新脚本；该页面不走 Cloudflare HTML 缓存。首页 HTML 可能缓存四小时，从旧首页通过 SPA 导航进入后台时，应在账号管理页再刷新一次。

## 检测间隔与点数

在模型归因弹窗设置「检测间隔」，按分钟输入 1–1440 的整数，默认 10。只改变间隔时，当前轮次继续执行，连续不符计数和自动停止状态保留；下一轮改为保存时间加所设间隔。首次开启仍会尽快检测。每次领取任务按该账号间隔安排后续轮次，全局只有一个检测 worker，不重叠、不补发遗漏的轮次，检测繁忙时可能晚于设定时间。

5h/7d 用量百分比不能代表剩余点数，因此不再用「已使用 90%」提前跳过。账号即使用量显示 100%，只要未处于实际限流/冷却且可调度，仍尝试检测，由上游决定是否可用。实际请求失败记为黄色，不会计入自动停止所需的红点。探针可能消耗点数；短间隔会增加消耗。

## 对现有业务的边界

- 原模型归因除用户开启的自动停调度外不改业务表。新提示词测试使用 GN2API 原生测试接口，保留原生用量快照、401 错误标记和 429 限流保护；`mode=attribution` 成功后不会运行手工连通性测试的账号恢复逻辑。扩展不会自动恢复已停止的账号调度。
- 新 Linux/PostgreSQL 同名用户 `modeltrace_ovh` 使用本机 peer 认证；数据库只授予 accounts/proxies 必要列 SELECT，无 users/账务表访问、无写权限。数据库只读账号仍属于敏感权限，应保留目录和系统用户隔离。
- 每条探针重新读取当前 access token/API key，只用于已选账号；不取 refresh token、不主动刷新 OAuth、不把上游凭据发送到浏览器或保存进 SQLite。
- 每轮固定账号和模型，使用该账号的代理。代理失效时跳过，不改用直连。中途路由/密钥变化时本轮作废。
- 全局单个检测 worker，无并发探针；每轮通常为所选的 1、2、3 次请求，数字样本不足补采和疑似不符复测合计最多 2、4、6 次；无 HTTP/协议/换号重试。
- 关闭或换模型会变更任务代次，阻止后续探针和旧结果写入。已经开始的上游请求可能已计费，取消无法撤销这笔用量。
- 账号不可调度、实际限流、冷却或 token 接近过期时跳过。5h/7d 用量百分比及正常业务请求不会导致跳过整轮。探针仍共享账号额度、点数与出口带宽，使用单 worker 和低资源优先级控制影响。
- 服务器负载高时推迟。不会为追赶漏过轮次而补发请求；账号过多时可能晚于设置的间隔。
- 单轮预算 240 秒；建连超时最多 8 秒，响应/流读取静默超时最多 120 秒（按本轮剩余时间缩短），输出流上限 2 MiB。接收数据和新请求前检查总预算，超预算不能得到有效归因；底层正在阻塞读取时可能到读取超时才退出。OAuth 不支持输出 token 参数，使用流/时间限制；其他协议设置输出 token 限制。
- 独立服务 CPU 上限 20% 单核、内存上限 256 MiB、Nice 15。它不限制 sub2api/CPA 的带宽或资源。
- 默认 10 分钟间隔、3 次挑战时，单账号单模型通常为 432 次探针/天；选择 1、2 次则通常为 144、288 次/天。补采及复测会增加消耗；间隔改变后消耗相应变化。所有账号默认关闭。

管理员鉴权复用 sub2api 的 `/api/v1/admin/system/version`；支持后台 JWT，认证成功最多缓存 10 秒。接口没有开放跨站访问；不保存浏览器传入的管理员 token。监听端口只绑定回环地址。

## 运维

查看状态：

```sh
sudo systemctl status modeltrace-ovh --no-pager
sudo systemctl show modeltrace-ovh -p MemoryCurrent -p MemoryPeak
sudo journalctl -u modeltrace-ovh -n 30 --no-pager
```

独立服务的修改只需重新启动 `modeltrace-ovh`；不应重新启动 sub2api、Nginx 或服务器。发布 Nginx 变更先 `nginx -t`，再 `systemctl reload nginx`，保留正在处理的旧连接。不要加入强制结束旧 worker 的超时。

Codex 客户端版本来自安装时 sub2api 已同步值，记录于环境文件。上游协议变化时需要同步更新该值或适配器。更新指纹库应固定版本、保留 LICENSE，并重新验证阈值和支持模型；不要自动拉取执行 main。

备份需包含 `/opt/modeltrace-ovh`、`/var/lib/modeltrace-ovh`、环境文件、`/etc/modeltrace-ovh` 凭据目录、systemd 单元及其 drop-in、前端脚本。含管理员凭据的备份必须保持 root 私有。SQLite 运行中应使用 `.backup` API/命令得到一致快照，不要只复制活跃的主数据库文件而漏掉 WAL。sub2api 自身的数据备份不包含这些独立文件。

停用时先关闭或停止 `modeltrace-ovh`，再移除 Nginx 中标注的扩展路由与脚本注入，配置检查后平滑 reload。历史数据库可以保留。不要盲目覆盖原 Nginx 备份，以免抹掉此后其他变更。
